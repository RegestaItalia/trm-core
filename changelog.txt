2026-10-19 v11.0.0
-------------------
! requires trm-server 8.0.0 (transport layers API); a trm-server/trm-rest upgrade still runs on an older backend
! upgrade deletes only the objects and customizing the new release no longer ships (was: the whole previous release before the import)
! upgrade/uninstall back up what may be deleted in @X1@TRM (BKP) transports, kept in the import queue for recovery and re-imported by a rollback
! deletions are generated by the registry from the backups (POST /delete options: target, subtract, exclude) into @X1@TRM (DELE) transports
! deletions are carried by the single landscape transport (TR_COPY): no deletion transport is forwarded to the target, no upgrade= comment
! landscape transport released last, after the install is recorded: a failed release no longer rolls back the install/uninstall
! uninstall generates a landscape transport (@X1@TRM (DELE)), nested uninstalls carried by the parent's
! AbstractRegistry.delete(transport, options?) returns the deletion transport and what it deletes
! imports fail from return code 8 (test, batch, deletion, restore); queue maxrc combined with the final tp return code
+ ignoreImportErrors install/uninstall option: return codes from 8 logged as errors instead of failing
+ customizing kept when shipped by a skipped transport or declined; generic keys confirmed with default no
+ final summary of transports imported, deleted, backed up and the landscape transport
+ empty deletion dummies and rolled back dummies taken out of the import queue
! import polling reads the request status, adaptive interval, progress with elapsed time
! connection checked at most once a minute
! TADIR entries written after import only where they differ
- uninstall forward-deletion-transport step, generate-update-transport and generate-post-import-update-transport steps
* SAP message placeholders (e.g. XT 153 destination) filled correctly
* batch import status shows the polled transport
* backup export checked before deleting
* action lock keys deduplicated
+ set-transport-layer install step: new packages get a transport layer routed to the landscape target (input, only routed layer or choice); an existing package not routed fails the install early
+ getTransportLayers connector API (trm-server /ATRM/GET_TRANSPORT_LAYERS, trm-rest get_transport_layers)
! backend API generations (TRM_BACKEND_APIS) replace the legacy backend flag
! staging packages of local ($) installations use a transport layer routed out of the system (default if routed), checked before any object is moved
! objects of a namespace missing on the system are staged in a customer package, without importing the namespace (imported only on a backend older than trm-server 7.0.0)
+ simulate install and publish: every check and question runs, nothing is changed, what would happen is logged
! upgrade deletion subtracts every repository transport of the incoming release (DEVC and LANG too, not only TADIR)
! upgrade cleanup: local objects in kept packages listed as not shipped and deleted; generated objects (e.g. CDS SQL views) left to their generating object
! publish: input post activities replace the latest release ones, the same class can run more than once
! TRM transport descriptions shared (trmTransportDescription, deletionDescription): deletion dummies keep their text after import
! registry deletion errors logged with the registry message and the action continues without them
- RegistryDeletionTransportUnauthorizedError
+ tp failures tell whether tp or the transport tools failed (TransportTmsError, parseTpLog)
! objects locked in transports shown as a single table
! workflow and step names only in the debug log
* release log: only the current export is read, a failed backup export with a reused request number was reported as released
* release waits for its own export to end: a reused request number could send a truncated transport to the registry on rollback
* STMS request text refreshed after release
